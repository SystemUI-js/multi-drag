## Context

Demo 当前由 `apps/demo/src/main.ts` 一次性创建页面 DOM，并在随后获取固定元素、初始化 `Drag` / `Mixin` 实例以及注册压力事件监听器。国际化实现必须保持这些 DOM 节点及其事件绑定稳定，不能因语言切换重新创建拖拽区域。需求见 `specs/demo-internationalization/spec.md`，变更动机见 `proposal.md`。

Demo 使用原生 TypeScript、DOM API 和 Vite，没有 UI 框架，也没有现成的国际化依赖或测试脚本。因此实现应保持轻量，利用 TypeScript 约束两套资源的键和值完整对应。

## Goals / Non-Goals

**Goals:**

- 将 Demo 的用户可见文案集中到类型安全的 `zh-CN`、`en-US` 资源中。
- 提供读取当前语言、获取翻译和切换语言的最小 API。
- 语言切换只更新文案及切换控件状态，不替换已经绑定拖拽行为的 DOM 节点。
- 通过语义化按钮、当前态和 `aria-pressed` 提供可操作、可感知的语言切换入口。

**Non-Goals:**

- 不引入第三方 i18n 运行时、按需加载、复数规则、插值、日期或数字格式化能力。
- 不持久化语言选择，也不根据浏览器语言自动选择；首次加载固定使用 `zh-CN`，行为可预测且与当前以中文为主的界面一致。
- 不修改拖拽库 API、拖拽参数或拖拽实例的生命周期。

## Decisions

### 1. 使用静态资源模块和联合类型约束资源键

在 `apps/demo/src/locales/` 下分别维护 `zh-CN.ts` 和 `en-US.ts`。中文资源作为资源结构的基准，导出其键联合类型；英文资源使用 `Record<TranslationKey, string>`（或等价的 `satisfies` 约束）校验，确保编译时发现缺失键、多余键和非字符串值。

相比单个嵌套对象，独立语言文件更便于维护和审阅；相比 JSON，TypeScript 模块无需额外的导入配置，并可直接获得静态键检查。当前文案规模较小，使用扁平的语义键（例如 `hero.title`、`pressure.description`）即可，避免引入嵌套查找逻辑。

### 2. i18n 模块只管理语言状态和文本访问

新增 `apps/demo/src/i18n.ts`，声明受支持语言联合类型和只读语言列表，并提供：

- `getLocale()`：读取当前语言；
- `setLocale(locale)`：切换到受支持语言；
- `t(key)`：从当前语言资源读取文本。

初始语言为 `zh-CN`。`setLocale` 只负责更新模块内状态，不直接操作页面，也不包含拖拽相关逻辑。调用方在切换后显式刷新页面文案，使状态模块可独立验证，且避免隐藏的 DOM 副作用。

备选方案是引入事件订阅或第三方 i18n 库；前者对目前唯一调用方增加了不必要的生命周期管理，后者违反无新增运行时依赖的约束，因此不采用。

### 3. 页面 DOM 只创建一次，切换时原位更新文本

`main.ts` 首次渲染时通过 `t()` 填充模板，并为所有国际化文本节点添加 `data-i18n` 标记。语言按钮使用稳定的 `data-locale` 标记。切换时执行一个页面级更新函数：

1. 调用 `setLocale` 更新语言状态；
2. 遍历 `[data-i18n]` 元素，根据标记调用 `t()` 并设置 `textContent`；
3. 更新 `document.documentElement.lang`；
4. 更新两个语言按钮的当前态样式和 `aria-pressed`。

如控件存在需要翻译的无障碍名称，则使用独立的属性标记更新 `aria-label`，不把 HTML 字符串写入翻译资源。

不采用切换后重设 `appElement.innerHTML` 的方案，因为这会销毁原有节点，使 `Drag` / `Mixin` 实例和事件监听器继续引用已脱离文档的元素，并破坏用户当前的拖拽位置与交互状态。原位更新 `textContent` 可保持全部节点身份和绑定不变。

### 4. 语言入口放入 Hero 顶部，并沿用现有视觉体系

Hero 内增加标题区与语言切换控件的布局容器。控件由两个原生 `button` 组成，显示“中”和“EN”，通过背景、边框或文字颜色区分当前项，同时支持键盘焦点样式。窄屏时布局允许换行，避免与标题重叠。

选择两个按钮而非自定义下拉菜单，是因为目前仅有两种语言；按钮组操作步骤更少，也能直接表达当前状态。具体颜色、圆角和间距沿用 Demo 现有深色、靛蓝色设计变量，不建立新的完整设计系统。

### 5. 验证以静态类型、构建和可重复的 DOM 行为检查为主

Demo 当前没有测试脚本。实现时至少运行 Demo 构建，使 TypeScript/Vite 验证资源键完整性和模块集成。另对页面执行人工或浏览器级检查：初始中文完整、双向切换后文案和按钮状态正确、切换无需刷新，以及切换前后所有拖拽示例仍可操作。

若现有仓库测试基础设施可以低成本复用，可增加针对纯 i18n 模块的单元测试；本变更不为 Demo 单独引入测试框架。

## Risks / Trade-offs

- [新增文案时只在一套资源中维护] → 使用共享的 `TranslationKey` 和 `Record` 类型让构建阶段失败。
- [动态标记包含未知资源键] → 在模板中以受类型约束的辅助函数生成标记，或在更新函数中对键做显式断言并在开发环境抛出清晰错误。
- [切换语言导致拖拽状态丢失] → 永不重新赋值页面根节点的 `innerHTML`，只原位更新文案节点与按钮属性。
- [英文文案变长导致布局拥挤] → 标题区允许换行，拖拽卡片保留弹性尺寸，并在窄屏下检查按钮与标题布局。
- [不持久化语言使刷新后恢复中文] → 这是本次刻意限定的范围；未来如有需求可在 `i18n.ts` 的初始化和 `setLocale` 中增加持久化，不改变资源结构或页面更新策略。

## Migration Plan

1. 新增两套语言资源和 i18n 状态模块。
2. 为现有模板文案替换为资源访问，并添加稳定的国际化标记与语言入口。
3. 添加语言切换后的原位刷新逻辑和控件样式。
4. 运行 Demo 构建并验证两种语言和拖拽交互。

该变更只影响 Demo，不涉及数据迁移或库版本兼容。若需回滚，可删除新增模块并恢复 `main.ts`、`style.css`；拖拽包本身无须回滚。
